# MATMA Python — CLI contract and troubleshooting

MATMA is an installed **developer tool**, not an application runtime library. Its source is
`https://github.com/rzepeda/matma-py`. The current code is the completed Phase 6
implementation on `main`, version `0.1.0.dev0` (not a released PyPI package).
Python >=3.11, PyYAML, and pytest (to execute tests) are needed.

## Install once in the consumer project's development environment

From an activated Python 3.11+ virtual environment:

```bash
python -m pip install "git+https://github.com/rzepeda/matma-py.git@main"
python -m pip install pytest
python -m matma --help
```

If GitHub access is restricted or a stable local checkout is preferred:

```bash
python -m pip install -e "/absolute/path/to/matma-py"
python -m pip install pytest
```

Use `python -m matma` in the examples: it uses the current environment's interpreter.
`matma-indexer` is an equivalent console command when available on `PATH`.
Do not install development tools into the application's production deployment.
MATMA has no published PyPI release or declared license; do not claim otherwise.

## Daily CLI commands (run at the CONSUMER project root)

```bash
python -m matma validate --check --format json
python -m matma index --format json
python -m matma scaffold --target pkg.pricing --format json
python -m matma impact --target pkg.pricing --level 2 --format json
```

`index --scaffold --target pkg.pricing` combines full reindex and scoped
scaffolding. `index --target ...` **still indexes the entire project**;
`--target` is a response filter. Use `scaffold --target ...` to restrict which
module gets newly generated test files. A target can be a project-relative
`.py` path (`src/pkg/pricing.py`), Python module name (`pkg.pricing`), or an
indexed qualified symbol (`pkg.pricing.PriceCalculator`).

MATMA discovers `src/`, common setuptools layouts, or a flat project. For
special layouts, configure the host project's existing `pyproject.toml`:

```toml
[tool.matma]
source_roots = ["src", "plugins"]
```

Or pass `--source-root src --extra-source-root plugins` to each relevant
command, and `--tests-root qa` for nondefault test folders. Keep the settings
consistent across `validate`, `index`, `scaffold`, and `impact`.

## Files created by MATMA

For `src/pkg/pricing.py`:

```text
tests/mirror/.index.auto.yaml
tests/mirror/src/pkg/pricing.auto.yaml
tests/unit/mirror/src/pkg/test_pricing.py
tests/interaction/mirror/src/pkg/test_pricing_interaction.py
tests/mocks/mirror/src/pkg/mock_pricing.py
```

`index` generates the `.auto.yaml` manifests, not pytest files. `scaffold`
creates only **missing** starter test/mock files; any existing test/mock file
is developer-owned and is never overwritten. Generated unit/interaction tests
contain deliberate `pytest.fail` placeholders. They do not represent passing
coverage. Replace those with meaningful assertions **before** treating CI
as green; run pytest explicitly only when requested or when the development
task includes test execution. Do not mark them `skip`/`xfail` solely to hide
template failures.

For mocks, patch where the *consumer looks up the name*, and prefer the
`unittest.mock.create_autospec` helpers that MATMA generated. Autospec factory
calls may import a source object at test runtime; indexing/scaffolding does not.

## Impact levels and result handling

| Requested level | Inclusive selection |
| --- | --- |
| `0` | Existing unit test for the target module |
| `1` | Level 0 plus interaction tests and directly used dependents |
| `2` | All lower levels plus imported-but-unused dependents and depth-two usage chains |
| `N` | All dependents at weighted graph distance <= N |

Import-only edges count as weight **2**, not weight 1. Static analysis is
conservative: dynamic imports, reflection and monkey-patching may require
additional business/regression verification.

Read the `impact` JSON fields:

- `status`, `exit_code`, `target`, `level`, `affected_sources`
- `tests.unit`, `tests.interaction`: **existing** pytest paths
- `tests.missing`: expected test paths **not** present, with source/tier/level
- `verification.business`, `verification.regression`: only explicitly registered paths
- `verification.missing`, `warnings`, `analysis_limits`

Report missing test paths separately. Never claim an affected test passed
because MATMA selected its filename. Do not automatically run pytest as part
of `impact`: MATMA only returns candidate paths.

## Optional developer-authored verification registry

Create and commit `tests/matma-verification.yaml` (never generated by MATMA):

```yaml
schema_version: 1
registrations:
  pkg.pricing:
    business:
      - tests/business/test_checkout.py
    regression:
      - tests/regression/test_rounding.py
```

Each listed path must be an explicit `.py` file inside the configured test
root. MATMA does not infer business tests by naming, nor automatically run
registered tests. If the consumer has business/regression workflows that are
not registered, raise that coverage limitation.

## Exit codes and recovery

| Exit | Meaning and agent action |
| --- | --- |
| 0 | Inspect the machine-readable `status` and diagnostics; success does not imply tests ran |
| 1 | Semantic/unsafe/stale failure; stop and report or fix the cause |
| 64 | Invalid options; correct command syntax |

`validate --check` fails for structural errors. `impact` fails with
`missing_index`, `stale_index`, `invalid_index`, or `invalid_target` when
appropriate. Run `index` explicitly after production source changes, added
modules, or changed root configuration, and retry the read-only impact query.
Do not delete or override user-owned YAML to bypass an `unsafe_output` error.
Existing generated manifests may be regenerated by MATMA; authored tests
must be preserved. Source directory freshness and byte hashes are checked;
impact is not O(1) end-to-end, though it avoids reparsing AST.

## Honest final report

Include: configured source roots, commands and exit codes, index freshness,
selected existing test paths, missing paths, newly created/retained scaffold
files, business/regression registrations, static-analysis warnings, and
pytest results **only if pytest was actually executed**. Never report
intentional placeholder failures as engine failures or passing tests.
